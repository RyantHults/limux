## AppImage CI Build Issue

**Status**: Resolved (committed)  
**Priority**: High  
**Created**: 2026-07-30  
**Resolved**: 2026-07-30 (original root cause) / 2026-08-03 (AppRun clobbering follow-up)

### Problem (original, superseded)

The CI-built AppImage (`limux-0.2.1-x86_64.AppImage`) was reported to fail to launch on non-NixOS systems, with the hypothesis that 89/90 bundled libraries were broken symlinks to `/nix/store/` paths.

### Actual Root Cause (different from original hypothesis)

The `dist/limux-0.2.1-x86_64.AppImage` artifact is **not an AppImage at all** — it's a stripped, static-pie `limux` binary. There is no squashfs payload, so there are no symlinks (broken or otherwise) to inspect. The "89/90 broken symlinks" claim was a misdiagnosis based on inspecting this stale file.

The bug is in `scripts/build-appimage.sh`'s AppImage-sealing step (lines 754-781 at the time of fix). `APPDIR` is created via `mktemp -d -t limux-appdir-XXXXXX` (line 82), so its basename is `limux-appdir-AbCdEf`. `linuxdeploy --output appimage` names its output `<appdir-basename>-<arch>.AppImage` in `$PWD` — i.e. `limux-appdir-AbCdEf-x86_64.AppImage`. But the post-run search loop hardcoded `limux-x86_64.AppImage` (no `appdir-` prefix) and never found the real file. The over-broad fallback `find` then picked up a stale file from a prior failed run and `mv`'d it to `dist/`. The validation step (none at the time) didn't catch it.

**Evidence confirming**:
- `file dist/limux-0.2.1-x86_64.AppImage` → `ELF ... static-pie linked, stripped` (no interpreter, no embedded AppImage)
- `ldd dist/limux-0.2.1-x86_64.AppImage` → `not a dynamic executable`
- Direct execution → `cannot execute binary file`

### Fix (uncommitted, see git diff)

Three changes to `scripts/build-appimage.sh`:
1. Search loop constructs the expected filename from `$(basename "$APPDIR")` instead of hardcoding `limux-`
2. Fallback `find` is scoped to `${APPDIR_BASENAME}*.AppImage` and picks the newest match
3. After `mv`, validate the output with `file(1)`; reject + `exit 1` if it's not a valid AppImage

One change to `.github/workflows/release-appimage.yml`:
- New "Verify AppImage structure" step after the build: runs `file`, `unsquashfs`, counts real `.so*` files vs symlinks, fails on any `/nix/store` symlink. Catches packaging regressions at CI time and also guards against the original misdiagnosis scenario.

### Follow-up (2026-08-03): AppRun clobbering breaks browser panels

While verifying the v0.2.3 release artifact, a second packaging bug surfaced: the seal step
(`linuxdeploy --output appimage`) regenerates linuxdeploy's autogenerated `AppRun` on every
invocation, silently discarding the custom AppRun written in Step 4 (which creates the
`/tmp/limux-webkit-helpers` sentinel, exports `WEBKIT_*` env, `LD_LIBRARY_PATH`, `LIMUX_SOCKET`,
and handles `--install`). Empirically reproduced: `open_browser` on the released AppImage aborts
the app fatally — `WebKitNetworkProcess` can't load `libwebkitgtk-6.0.so.4` and the WebKit
sandbox (`bwrap`) is never disabled.

Fix (committed):
1. `scripts/build-appimage.sh` — seal with `appimagetool` instead of `linuxdeploy --output appimage`
   (appimagetool squashes the AppDir as-is, preserving the custom AppRun); unify the nix and
   system paths; keep the `hsqs` magic validation. Also export `WEBKIT_INJECTED_BUNDLE_PATH` in
   the custom AppRun.
2. `app/src/main.rs` — new `setup_appimage_webkit()` safety net: when `APPDIR` is set, recreate
   the `/tmp/limux-webkit-helpers` sentinel symlink and export the WebKit env vars from inside the
   binary, so browser panels work even if a launcher script is bypassed or clobbered again.
   Validated: applying this env/sentinel setup to the v0.2.3 image makes `open_browser` succeed.
